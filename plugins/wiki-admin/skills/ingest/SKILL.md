# ingest

把 Sources 里状态为「待处理」的材料提炼成 Wiki 页面（即 Wiki Index 条目，ADR 0007）。
**用户确认之前不修改 Notion。** 新知识点和已有页面的关系分三种：

- 没有对应页面：新建页面
- 和已有页面一致、只是补充：经用户确认后，把补充内容追加到已有页面
- 和已有页面说法不一致：**不改已有页面**，只记入 Conflicts（NEG-001），由用户用 `/wiki-admin:resolve-conflict` 处理

调用 `notion-*` 工具的前置条件、写入格式和报错处理见 [Notion 工具使用约定](../../references/notion-tools.md)。
新增 multi_select 选项要在第 6 步的建议里列出来，让用户一并确认。

## 步骤

1. **定位 Wiki**：按 [定位 Wiki](../../references/locate-wiki.md) 找到根页面，取出 Sources、Wiki Index、
   Wiki Changelog、Conflicts 的 data source ID。

2. **找待处理材料**：用 `notion-query-data-sources` 查询 Sources，筛选「状态」= 待处理。
   没有结果时告诉用户「没有待处理的材料」，结束，不做任何修改。

3. **读取内容**：对每条材料用 `notion-fetch` 读取页面正文（文章正文、视频文字稿、图片描述）。
   正文为空但有「链接」时，用 WebFetch 读取链接内容。两者都没有可用内容时跳过这条，在汇报中说明原因。

4. **提炼知识点**：每个知识点准备：
   - 标题：简短的名词短语
   - 分类：concepts（概念、原理）、techniques（方法、流程）、tools（软件、框架、库）之一
   - 领域标签：沿用材料的领域标签，必要时补充
   - 简短摘要：一两句话
   - 正文：要点、原理或步骤、出处。techniques 要写清步骤、所需工具和前置条件，`/sync-skills` 会读取它们

5. **查重与冲突检测**：对每个知识点，查询 Wiki Index，找标题相同或明显是同一主题的已有页面，
   用 `notion-fetch` 读它的正文，并**记下它的最后编辑时间**（第 8 步用来核对 NEG-001）。按下面的情况处理：
   - 已有页面的「来源材料」已包含这条材料：说明之前写入过，跳过这个知识点
   - 内容一致，没有新东西：不修改，列为相关页面
   - 内容一致，新知识点有已有页面没写的内容：标为「追加到已有页面」，准备要追加的段落
   - 说法不一致：按 [冲突分类标准](references/conflict-types.md) 判断类型，准备一条冲突记录。
     这个知识点**不写入 Wiki**，也不修改已有页面。一个知识点和已有页面有几处不一致，就准备几条冲突记录
   - 没有对应的已有页面：标为「新建」

   **同一批里的知识点也要互相比较**：不同材料提炼出同一主题的知识点时，先出现的按上面的规则处理，
   后出现的把先出现的当作"已有页面"来比较。如果先出现的是新建页面，冲突记录就关联到这个新页面
   （写入时先建页面、再建冲突记录）。

   **去重**：查 Conflicts，已有一条记录的 Wiki 页面、新材料都相同，并且冲突摘要说的是同一处不一致时，不重复创建。
   同一页面、同一材料的不同不一致之处，各建一条。

   **查证事实性冲突**：对准备好的每条事实性冲突，按 [证据核验](references/evidence.md) 查证，
   得到证据链接、强度评分和推荐方案。查证范围和限制见该文。

6. **展示建议并等待确认**：按材料分组列出：
   - 拟新建的页面（标题、分类、领域标签、摘要）
   - 拟追加到已有页面的内容（已有页面链接、要追加的段落）
   - 拟创建的冲突记录（冲突摘要、类型、判定理由、推荐方案）；事实性冲突附上证据链接、强度评分和关键原话；
     「无法判断」和「证据不足」的单独列出，提示用户人工判断
   - 涉及但不修改的已有页面
   - 需要新增的 multi_select 选项

   问用户：「是否按以上建议写入？」用户可以删减条目，也可以改冲突类型。
   **只有用户明确回答「是 / 确认 / 继续」后才写入。** 用户拒绝时结束，不做任何修改。

7. **写入**：逐条材料处理：
   1. 用 `notion-create-pages` 在 Wiki Index 中新建页面（parent 用 Wiki Index 的 data source ID），
      属性填标题、分类、领域标签、简短摘要，「来源材料」填这条材料的页面 URL。
   2. 正文末尾加「相关页面」一节，用 `<mention url="..." />` 提及相关页面。
      同一批新建的页面互相提及时，先把页面都建好，再用 `notion-update-page` 追加这一节。
   3. 在 Wiki Changelog 中为每个新页面建一条记录：变更摘要「新建：<标题>」、Wiki 页面、来源材料、
      变更类型「新建」、详情（一句话说明提炼自哪条材料）。
   4. 追加到已有页面：用 `notion-update-page` 的 `insert_content` 把补充段落加到页面末尾（「相关页面」之前），
      并把这条材料加进它的「来源材料」（保留原有的值）。在 Changelog 中建一条记录：
      变更摘要「更新：<标题>」、变更类型「更新」、详情写追加了什么。
   5. 在 Conflicts 中按冲突分类标准的「冲突记录写什么」一节创建冲突记录（parent 用 Conflicts 的 data source ID），
      正文里附上**完整的新知识点**（第 4 步提炼的标题、分类、正文），冲突解决后据此写入 Wiki。
      冲突记录不写 Changelog：Wiki 内容还没变，解决冲突时再记。
   6. 这条材料的页面、Changelog 和冲突记录都写完后，用 `notion-update-page` 把它在 Sources 中的「状态」改为「已入库」。
      即使有未解决的冲突（「待审核」或「待人工审核」）也改为「已入库」：材料已经处理过，未决的部分由 Conflicts 跟踪。

8. **核对**：用 `notion-fetch` 回读新建的页面、追加过的页面和冲突记录，确认属性和关联正确，
   并检查正文和摘要里没有 `http://<文件名>` 这类被误识别的链接，有就改成反引号写法。
   再查一次被冲突的已有页面的最后编辑时间，和第 5 步记下的对比，应该没有变化（NEG-001）。
   有变化时停下，告诉用户哪个页面在入库期间被改过、改动时间，不要自动恢复：可能是用户自己在 Notion 里改的。

## 失败处理

工具报错（`rate_limited`、`usage_limit_reached` 等）按 [Notion 工具使用约定](../../references/notion-tools.md) 处理。

- 写到一半失败：停止，列出已写入的页面、追加过的页面、Changelog、冲突记录，以及失败原因。
  这条材料的状态保持「待处理」；重新运行时，第 5 步会跳过已经写入的知识点和已经存在的冲突记录。

## 汇报

结束时列出：

- 处理了哪些材料，跳过了哪些（附原因）
- 新建的 Wiki 页面链接（按分类分组）
- 追加过内容的已有页面
- 新建的冲突记录链接（按类型分组），「无法判断」的提醒用户手动分类
- 涉及但未修改的已有页面
- 写入的 Changelog 条数
- 状态改为「已入库」的材料
