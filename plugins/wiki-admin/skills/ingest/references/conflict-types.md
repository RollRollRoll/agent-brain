# 冲突分类标准

`/wiki-admin:ingest` 按本文判断新知识点和已有 Wiki 页面是否冲突、属于哪一类。

分类和推荐方案依据 ADR 0004。事实性冲突的查证规则见 [证据核验](evidence.md)。与 ADR 0004 有一处不同：

- ADR 0004 的状态列了「已忽略」，Conflicts 数据库目前只有「待审核」「待人工审核」「已解决」。需要「已忽略」时，先给数据库加上这个选项

## 什么算冲突

新知识点和已有页面说的是**同一件事**，但结论、数据、建议或描述不一致。

不算冲突的情况（`ingest` 会把补充内容追加到已有页面，不建冲突记录）：

- 新知识点只是补充了已有页面没提到的内容，两者不矛盾
- 两者说的是不同的东西，只是标题或用词相近

## 分类

按下面的顺序判断，取第一个符合的类型。

| 类型 | 判定条件 | 示例（新 vs 已有） | 推荐方案 |
|---|---|---|---|
| 时效性 | 两边描述的是**不同时间点或不同版本下各自成立**的状态，差异来自时间推移或版本演进，两者在各自的时间点上都对。只是都出现了日期或版本号不算：如果两边说的是同一个时间点的同一件事（比如同一个事件发生在哪一年），归为事实性 | "2025 年推荐用 Vite" vs "2024 年推荐用 Webpack"；"v2 用新端点" vs "v1 用旧端点" | 保留旧内容为历史，突出新内容，标注时间或版本 |
| 场景性 | 两者各自限定了适用条件（规模、平台、用途），条件不同 | "大项目用 PostgreSQL" vs "小项目用 SQLite" | 不替换，补充为「按场景选择」，写明各自的适用条件 |
| 深度性 | 一个是简化版、一个是完整版，或者分别面向入门和进阶 | "快速上手用默认设置" vs "逐个说明每个参数" | 不替换，两者都保留，标注难度层次（入门 / 进阶 / 专家） |
| 事实性 | 关于可以客观验证的事实（数字、日期、是否支持某功能、出处原文），同一件事说法不一致，最多只有一边是对的 | "Python 3.12 发布于 2023 年" vs "2024 年"（同一个发布事件，不是时效性） | 按[证据核验](evidence.md)查证，按证据推荐采纳哪一方；不改 Wiki |
| 观点性 | 主观评价或偏好不同，没有客观标准 | "VSCode 最好用" vs "Vim 最好用" | 不做判断，两种观点都保留，各自标注来源 |
| 无法判断 | 以上都不符合，或者在两个类型之间拿不准（置信度低于 50%） | | 不给推荐，交给用户手动分类 |

先判断时效性、场景性、深度性，是因为这三类看起来像事实冲突，其实可以共存。
判断依据是「两边能不能同时成立」，不是表面有没有日期、条件或难度词：能同时成立才归这三类，
只能有一边对的，归为事实性或观点性。

## 冲突记录写什么

在 Conflicts 中每个冲突建一条记录：

| 字段 | 内容 |
|---|---|
| 冲突摘要 | 一句话，格式：`<主题>：<新说法> vs <原说法>` |
| Wiki 页面 | 被冲突的已有页面 |
| 冲突类型 | 上表中的类型 |
| 新材料 | 这条材料 |
| 原有内容摘要 | 已有页面中相关的原话或要点 |
| 新内容摘要 | 新材料中相关的原话或要点 |
| 状态 | 「无法判断」填「待人工审核」，其余填「待审核」 |

证据链接、证据强度评分：事实性冲突按[证据核验](evidence.md)填写，其他类型留空。
解决方案留空，在用户解决冲突时填写。

记录的**正文**写：

- **判定理由**：为什么归为这一类，引用双方的关键原话
- **推荐方案**：按上表；事实性冲突按证据核验的决策规则写；「无法判断」写「请手动分类」，并说明在哪两个类型之间拿不准
- **证据**（只有事实性冲突）：按证据核验的「记录」一步写
- **双方来源**：新材料的标题、作者、发布时间、链接（有就写）；已有页面的「来源材料」
- **待写入的新知识点**：第 4 步提炼的完整内容（标题、分类、领域标签、简短摘要、正文）。
  材料已经标为「已入库」，不会再被提炼，冲突解决后只能从这里取内容写入 Wiki
