# ADR 0005: Notion API 升级到 2026-03-11

**状态**：已被 ADR 0006 取代（2026-10-22）。项目不再直接调用 Notion REST API，API 版本由托管 MCP 处理。  
**日期**：2026-10-21  
**决策者**：用户

## 背景

REQ-001 要求 `/init-wiki` 为数据库配置 Board / Gallery 视图。Notion 的 Views API（`POST /v1/views`）
要求 API 版本 2025-09-03 或更新，接口参考页只接受 `2026-03-11`。项目最初锁定的是 `2022-06-28`。

2025-09-03 引入了 data source 模型：数据库是容器，schema 和条目属于其中的 data source，
两种 ID 不能互换。2026-03-11 又把 `archived` 改名为 `in_trash`，并把追加 block 的 `after` 参数改为 `position`。

## 决策

整个客户端统一使用 `Notion-Version: 2026-03-11`，按 data source 模型实现。

## 候选方案

- **A. 整体升级（采纳）**：一次改到新模型，视图由 `/init-wiki` 自动创建。
- **B. 混用版本**：常规请求保持 2022-06-28，只在建视图时发新版本头。改动最少，
  但代码里同时存在两套数据模型，后续仍需迁移。
- **C. 不建视图**：视图改为用户手动添加。

## 理由

- 当时只完成了 #2、#3，代码量小，迁移成本最低。
- #4 以后的工单都要查询数据库、往数据库里建条目，这些接口在新版本里路径和参数都变了；越晚升级，要改的地方越多。
- 只维护一套数据模型，避免 database_id / data_source_id 混用出错。

## 后果

对后续实现的约束：

- 建数据库：schema 放在 `initial_data_source.properties`，响应里的 `data_sources[0].id` 是 data source ID
  （响应可能是只含 `id` 的精简版，此时要再调用 Retrieve database）
- relation 属性只能写 `data_source_id`
- 查询条目：`POST /v1/data_sources/{data_source_id}/query`
- 往数据库里建条目：父级用 `{"type": "data_source_id", "data_source_id": ...}`
- 归档：`{"in_trash": true}`，读取时检查 `in_trash`
- 追加 block：用 `position` 对象，不再用 `after`
- 建视图要同时传 `database_id` 和 `data_source_id`；board 的 `group_by` 要用属性 ID，需先 Retrieve data source 取得
