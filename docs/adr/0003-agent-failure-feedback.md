# ADR 0003: Agent 失败反馈机制

**状态**：已接受  
**日期**：2026-10-21  
**决策者**：用户 + 技术推荐

## 背景

Agent 执行 skill 时可能失败，原因包括：
- Skill 中的工具路径错误
- 前置条件不满足（缺少依赖、权限不足）
- 输入数据格式不符合预期
- 外部服务不可用
- Skill 本身的逻辑错误

失败后如果没有反馈机制，相同的错误会重复发生，降低系统可用性。

## 决策

实现 Agent 失败反馈机制，包括：
1. **记录失败到 Agent Tasks 数据库**（Notion）
2. **LLM 分析失败原因**
3. **更新 Skill 或 Wiki**（根据失败类型）

## 实现细节

### 1. 失败记录结构

在 Notion 的"Agent Tasks"数据库中记录：
- **任务名**：用户请求的任务描述
- **使用的 Skill**：调用的 skill 名称（关联到 Git 仓库路径）
- **执行时间**：开始和结束时间
- **状态**：成功 / 失败 / 部分成功
- **结果摘要**：简短描述执行结果
- **失败原因**（如果失败）：错误消息、堆栈跟踪、Agent 的分析
- **反馈/问题**：Agent 或用户添加的后续反馈

### 2. 失败分类和处理策略

| 失败类型 | 处理策略 | 更新目标 |
|---------|---------|---------|
| **工具路径/配置错误** | 修正 skill 中的路径或配置 | 本地 Skill 文件 |
| **前置条件缺失** | 在 skill 中补充前置条件检查和提示 | 本地 Skill 文件 |
| **输入数据格式问题** | 更新 skill 的输入验证逻辑 | 本地 Skill 文件 |
| **知识不足** | Skill 依据的 Wiki 知识过时或错误 | Notion Wiki 页面 |
| **外部服务不可用** | 添加重试逻辑或降级方案 | 本地 Skill 文件 |
| **Skill 逻辑错误** | 修复 skill 实现 | 本地 Skill 文件 |

### 3. 反馈流程

**自动流程**（Agent 执行完任务后）：
1. Agent 将执行结果（成功/失败）记录到 Notion Agent Tasks 数据库
2. 如果失败，记录详细的错误信息和上下文

**人工介入流程**（定期或手动触发）：
1. 用户或 LLM 检查失败记录（可以按 skill 分组，识别高频失败）
2. LLM 分析失败原因，提出修复建议
3. 用户确认后，LLM 更新对应的 Skill 或 Wiki
4. 可选：重新运行失败的任务验证修复

### 4. 高频失败告警

如果同一个 skill 在短时间内（如 1 天）失败多次（如 3 次以上），触发告警：
- 在 Notion 的"Agent Tasks"数据库中标记该 skill 为"需要修复"
- 可选：暂时禁用该 skill，防止 Agent 重复调用失败的 skill

## 后果

### 优势
- **持续改进**：失败不是终点，而是改进的起点
- **减少重复失败**：修复后同类问题不再发生
- **可追溯性**：完整的失败记录可以回溯问题历史
- **优先级识别**：高频失败的 skill 优先修复

### 代价
- **需要维护反馈数据库**：增加了一个数据流（Agent → Notion → LLM → Skill/Wiki）
- **人工介入成本**：自动分析可能不准确，需要人工确认修复方案
- **复杂度增加**：失败分类和处理策略需要根据实际使用迭代

### 缓解措施
- 初期简化流程：只记录失败，人工检查和修复
- 稳定后增强：LLM 自动分析并提出修复 PR
- 设置告警阈值：避免过度干预（偶发失败不触发修复流程）

## 实现阶段

**阶段 1（MVP）**：
- Agent 记录失败到 Notion Agent Tasks 数据库
- 人工检查失败记录，手动修复 Skill

**阶段 2（半自动）**：
- LLM 分析失败原因，提出修复建议
- 用户确认后 LLM 更新 Skill/Wiki

**阶段 3（自动化）**：
- 高频失败自动触发告警
- LLM 自动修复简单问题（如路径错误、格式问题）

当前采用**阶段 1**，后续根据实际使用情况升级。

## 替代方案

### 方案 A：只记录失败，不主动修复（未采纳）
- Agent 记录失败到数据库，用户被动发现和修复
- 优点：实现简单
- 缺点：问题可能被忽略，重复失败影响体验

### 方案 B：Agent 失败时立即中断并要求人工介入（未采纳）
- 每次失败都暂停，等待用户处理
- 优点：确保每个问题都被处理
- 缺点：过度干预，打断用户工作流
