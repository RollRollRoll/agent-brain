# ADR 0004: 知识冲突处理机制

**状态**：已接受  
**日期**：2026-10-21  
**决策者**：用户

## 背景

当新的原始材料（文章、视频、论文）加入系统时,可能与已有 Wiki 内容产生冲突。例如：
- 新文章说"方法 A 最好"，但 Wiki 里说"方法 B 最好"
- 新论文提供的数据和旧材料不一致
- 不同作者对同一技术有不同理解

简单的处理方式（自动覆盖或只标记矛盾）都不够：
- **自动覆盖**：可能丢失有价值的旧知识
- **只标记矛盾**：无法指导用户如何解决
- **自动合并**：可能混淆不同场景或层次的知识

用户要求"需要一系列的分类判断、证据核验、历史保留机制"。

## 决策

实现分层的冲突处理机制：
1. **分类判断**：LLM 识别冲突类型
2. **证据核验**：根据类型采取不同的核验策略
3. **历史保留**：双层历史记录（Notion 原生 + 变更日志数据库）

## 1. 冲突分类

LLM 将冲突分为五类，每类有不同的处理策略：

### 事实性冲突（Factual Conflict）
**定义**：可客观验证的事实不一致  
**示例**：
- "Python 3.12 发布于 2023 年" vs "2024 年"
- "FFmpeg 支持 H.265 编码" vs "不支持"

**处理策略**：
- LLM 主动查证官方文档或可信来源
- 记录证据链接和关键引用
- 给出推荐方案（通常采纳更新、更权威的来源）
- 需要用户确认后才更新 Wiki

### 观点性冲突（Opinion Conflict）
**定义**：主观偏好或评价不同  
**示例**：
- "VSCode 是最好的编辑器" vs "Vim 最好"
- "这个剪辑风格很时尚" vs "过时了"

**处理策略**：
- 不做判断，两种观点都保留
- 标注来源和作者背景
- 在 Wiki 页面中以"不同观点"区块展示
- 不触发证据核验（因为没有客观标准）

### 时效性冲突（Temporal Conflict）
**定义**：新信息覆盖旧信息（领域最佳实践随时间演进）  
**示例**：
- "2024 年推荐用 Webpack" vs "2025 年推荐用 Vite"
- "旧版 API 用 v1 端点" vs "新版用 v2"

**处理策略**：
- 保留历史版本（通过变更日志数据库）
- 在 Wiki 页面中标注时间和版本
- 突出显示最新版本，旧版本移至"历史"区块
- 自动采纳新信息，但保留旧信息的可追溯性

### 场景性冲突（Contextual Conflict）
**定义**：不同场景下的不同建议（实际不是冲突，是补充）  
**示例**：
- "小项目用 SQLite" vs "大项目用 PostgreSQL"
- "入门用自动模式" vs "专业用手动模式"

**处理策略**：
- 识别为"场景差异"而非真正冲突
- 在 Wiki 页面中明确各自的适用场景
- 不替换，而是补充（"根据场景选择"区块）

### 深度性冲突（Depth Conflict）
**定义**：简化版 vs 完整版（实际是层次差异）  
**示例**：
- "入门教程：先学 HTML" vs "完整路线：先学计算机基础"
- "快速上手：用默认设置" vs "深入理解：每个参数的含义"

**处理策略**：
- 识别为"难度/深度层次"而非冲突
- 在 Wiki 页面中标注难度等级（入门/进阶/专家）
- 两者都保留，用户根据自己的层次选择

### 无法判断（Uncertain）
**定义**：LLM 无法确定冲突类型，或置信度低于 50%  
**处理策略**：标记为"需要人工审核"，不自动处理

## 2. 证据核验

### 对事实性冲突的主动查证
LLM 使用以下工具查证：
1. `web_search`：搜索官方文档、权威网站
2. `WebFetch`：抓取具体页面验证细节
3. 记录到冲突记录的"证据链接"字段

**证据强度评分**：
- **高（90-100%）**：官方文档、API 文档、语言规范
- **中（60-89%）**：知名博客（如 Martin Fowler）、权威教程（如 MDN）
- **低（< 60%）**：个人博客、论坛帖子、未注明来源的文章

**决策规则**：
- 高强度证据 > 中强度证据 > 低强度证据
- 同等强度时，优先采纳更新的（基于发布时间）

### 对其他冲突的来源记录
对于观点性、场景性、深度性冲突，记录：
- 新材料的来源（作者、发布时间、链接）
- 已有 Wiki 页面的来源（之前从哪份材料提炼的）
- 冲突的具体内容（对比两者的关键差异）

不主动查证，由用户根据来源可信度和自己的判断决定。

## 3. 历史保留

### 双层历史记录

#### 第一层：Notion 原生 Page History
- **由 Notion 自动维护**，每次更新都保留历史版本
- **优点**：零成本，防误改，可在 Notion UI 中回滚
- **缺点**：Notion API 不提供访问，LLM 和 Agent 无法读取

#### 第二层：Wiki Changelog 数据库
- **专门的 Notion 数据库**，记录所有 Wiki 变更
- **字段**：
  - Wiki 页面（关联 Wiki Index）
  - 变更时间
  - 来源材料（关联 Sources）
  - 变更类型（新建/更新/冲突解决）
  - 详情（摘要说明本次变更的内容和原因）
- **优点**：
  - 全局可查询（如"所有因冲突而修改的页面"）
  - LLM 和 Agent 可读取，用于追溯知识演进
  - 支持统计分析（如"哪些领域更新最频繁"）
- **缺点**：需要 LLM 额外维护

### 查询示例
- "视频剪辑相关的知识最近有哪些更新？" → 查询 Changelog，筛选领域标签
- "这个技术点为什么改了？" → 查询 Changelog，找到变更记录和来源材料
- "最近解决了哪些知识冲突？" → 查询 Changelog，筛选变更类型=冲突解决

## 4. 冲突解决流程

### 入库时的冲突检测（半自动）
1. LLM 读取待处理的原始材料
2. 提取关键知识点
3. **对比已有 Wiki 页面**，检测冲突
4. 如果有冲突：
   - 分类冲突类型
   - 对事实性冲突进行证据核验
   - 创建冲突记录（Conflicts 数据库）
   - 给出推荐的解决方案
5. **等待用户确认**后再更新 Wiki
6. 更新 Wiki 后记录到 Changelog

### 冲突记录的字段
Notion "Conflicts" 数据库包含：
- **Wiki 页面**（关联 Wiki Index）
- **冲突类型**（事实性/观点性/时效性/场景性/深度性/无法判断）
- **新材料**（关联 Sources）
- **原有内容摘要**
- **新内容摘要**
- **证据链接**（如果是事实性冲突）
- **证据强度评分**（如果有查证）
- **状态**（待审核/已解决/已忽略）
- **解决方案**（最终采纳的方案和理由）

### 用户审核和解决
用户定期检查"待审核"的冲突记录：
- 查看 LLM 的分类和推荐方案
- 查看证据链接（如果有）
- 决定：采纳新内容 / 保留旧内容 / 两者都保留 / 手动合并
- 确认后，LLM 更新 Wiki 并记录到 Changelog

## 后果

### 优势
- **细粒度处理**：不同类型的冲突用不同策略，避免一刀切
- **可追溯性**：完整的历史记录，知识演进过程清晰可查
- **证据驱动**：事实性冲突基于证据而非猜测
- **保留价值**：观点性和场景性知识不被错误覆盖

### 代价
- **复杂度高**：五种冲突类型、不同的处理策略、双层历史记录
- **需要人工介入**：半自动流程，用户需要审核和确认
- **维护成本**：需要维护 Conflicts 和 Changelog 两个数据库

### 缓解措施
- 初期 LLM 的分类建议可能不准确，用户可以重新分类
- 提供冲突记录的过滤和排序（优先处理高频领域的冲突）
- 定期清理已解决的冲突记录（归档到 Changelog）

## 实现阶段

**阶段 1（当前）**：
- 冲突分类（五类 + 无法判断）
- 事实性冲突的证据核验
- 双层历史记录
- 半自动流程（LLM 建议，用户确认）

**阶段 2（未来优化）**：
- LLM 自动解决低风险冲突（如明显的时效性冲突）
- 高频冲突模式识别（如"这个作者的材料经常和我们的 Wiki 冲突，可能是观点差异"）
- 冲突统计和报告（如"本月解决了 15 个冲突，其中 10 个是时效性更新"）
